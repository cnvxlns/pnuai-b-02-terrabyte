# 관수량 산출 설계

최종 갱신: 2026-08-17 (Asia/Seoul)
대상 이슈: #54 (데이터·평가 기준), #55 (관수량 산출), #48 (안전 게이트웨이)

> **우선순위**: 이 문서가 [`edge_ai_hardening.md`](edge_ai_hardening.md) §3.2–3.3과 충돌하면 **그 문서가 우선한다.**

## 0. 먼저 알아야 할 제약 — 우리는 관수량을 측정할 수 없다

**유량계가 없다.** 펌프는 단순 DC 모터이고, 시스템이 실제로 제어하는 값은 구동 시간이다.

```
mL = flow_ml_per_s × runtime_ms        # flow_ml_per_s = 8.0 (보정 전 가정값)
```

이 한 줄 위에 mL이라는 단위 전체가 얹혀 있다. 결과는 이렇다.

| | 사실 |
|---|---|
| 실제 전달 오차 | 헤드 높이·튜브 마모·전압·프라이밍 상태에 따라 **±20~40% 추정** |
| `device_command.actual_ml` | 엣지도 유량계가 없으므로 **같은 추정을 되돌려 보내는 값**. 부피에 대한 독립 정보가 아니다 |
| 실제로 강제되는 안전 한계 | **시간**이다. Arduino 펌웨어의 `millis()` 인터록(D18)이 최종 방어선 |

즉 `granted_ml: 118`의 물리적 의미는 **"14.75초 구동, 대략 90~150mL"**다. 화면과 API는 추정임이 드러나게 표기한다.

### 0.1. 이 제약이 무엇을 무효화하는가

- **연속값 예측은 과잉이다.** 액추에이터 해상도보다 정밀한 출력은 물리 세계에서 구분되지 않는다.
- **`actual_ml` 기반 재학습은 성립하지 않는다.** 자기 가정을 라벨로 삼는 순환이 된다 (§4.2).

### 0.2. 무엇은 무효화되지 않는가

- **Governor의 안전 한계는 그대로 유효하다.** 1회 200mL·24시간 600mL는 시간 한계가 mL 옷을 입은 것이고, 강제력은 손상되지 않는다.
- **예산을 실행 보고 기준으로 세는 원칙도 유효하다.** 다만 목적이 부피 정확도가 아니라 *"명령이 실행됐는가"*(유실·만료·엣지 자율분 반영)를 잡는 데 있다.

## 1. 결정: 학습 모델을 쓰지 않는다 (D27)

관수량은 **물수지 수식으로 직접 계산**한다. 학습된 회귀 모델은 배포하지 않는다.

### 근거 (독립적인 두 가지)

**1. 모델이 배우는 것이 없다.** 합성 라벨을 물수지 수식으로 만들었으므로, 모델이 하는 일은 그 수식을 되찾는 것이다. 원본 수식보다 **덜 정확하고**(MAE 16mL의 근사 오차), **더 크고**(gzip 557KB vs 코드 40줄), **덜 투명하다**(트리 76,044노드).

**2. 액추에이터 해상도가 모델 정밀도보다 거칠다** (§0). 이쪽이 더 강한 근거다 — 실측 데이터를 모으면 1번은 해소되지만 2번은 **하드웨어를 바꾸지 않는 한 남는다.**

### 합성 데이터 학습기는 남기지 않는다

합성 데이터로 학습하지 않기로 해놓고 합성 데이터 학습기를 보관하는 건 모순이다. 데이터 생성기와
회귀 학습 스크립트는 삭제했다.

남긴 것은 `edge/pi/tools/reference_water_balance.py` **하나**다. 배포되지 않고 엣지가 import하지도
않는다. `volume.py`가 이 파일의 손수 이식본이고, 이식 중 조용히 어긋나면 모든 관수량이 틀어지는데
잡아줄 게 없기 때문에, 테스트가 두 구현에 무작위 입력을 먹여 일치를 검증한다.

실측 데이터가 생기면 학습기는 그때 쓴다. 템플릿은 이미 있다 — `edge/pi/tools/train_irrigation_rf.py`가
같은 일(sklearn 학습 → `forest.py`가 읽는 JSON 내보내기 → skew 검증)을 분류기에 대해 하고 있고,
회귀는 그 변형이다. 존재하지 않는 데이터를 위해 지금 쓰는 건 추측이다.

## 2. 결정: 엣지에서 계산한다 (D28)

```
엣지가 매 주기 계산 → 텔레메트리에 실어 올림
                   ↓
서버 Governor 가 요청량으로 받아 게이트 7단 통과
                   ↓
값이 없거나 범위 밖이면 → 화분 크기 폴백표
```

### 근거

- 네트워크가 필요 없는 계산에 왕복을 넣을 이유가 없다. 서버 왕복이 오히려 느리다
- 컨테이너 하나와 `fastapi`·`uvicorn`·`sklearn`·`numpy`·`pandas` 의존성이 사라진다
- HTTP 실패 처리(타임아웃·스키마 불일치·503·폴백) 표면 전체가 사라진다
- 액추에이터가 생기면 오프라인에서도 관수량 산출이 가능해진다

### 설정은 아래가 아니라 **위로** 흐른다

화분 용적은 **물리적 설정**이다 — 어떤 화분을 꽂았는지는 엣지가 아는 게 자연스럽다. 서버에서 내려보내면 같은 값이 두 곳에 살아 드리프트가 생긴다. 엣지가 자기 설정을 텔레메트리에 실어 올리고, 서버가 자기 기록과 대조해 **불일치를 경고로 드러낸다.** 기록자가 하나이므로 조용히 어긋날 수 없다.

## 3. 계약

### 3.1. 엣지 → 서버 (envelope v2 노드 항목에 추가)

```json
"irrigation_suggestion": {
  "volume_ml": 118,
  "model_version": "water-balance-v1",
  "assumed_crop_code": "lettuce",
  "assumed_substrate_volume_ml": 3000
}
```

**선택 필드다.** 엣지가 계산할 수 없으면(토양수분 결측·범위 이탈, 화분 용적 미설정) **통째로 생략한다.** 없으면 서버가 폴백표를 쓴다 — 지어낸 숫자가 폴백을 밀어내면 안 된다.

`assumed_*` 두 필드는 드리프트 감지 전용이다. 서버는 이 값을 자기 `pot` 기록과 대조하고, 어긋나면 **양쪽 값을 적어 WARN을 남긴 뒤 그래도 제안값을 쓴다** — 물리적 용적은 엣지 쪽이 더 신뢰할 만하기 때문이다.

### 3.2. 서버 폴백표

| 화분 용적 | 기본 관수량 |
|---|---|
| ~1 L | 40 mL |
| 1–3 L | 80 mL |
| 3–6 L | 120 mL |
| 6 L~ | 160 mL |
| **미상** | **40 mL** |

미상일 때 가장 작은 값을 쓰는 이유: 높게 짐작하는 쪽이 화분을 넘치게 하는 실수다.

**제안값이 `[0, 500]` 밖이면 클램프하지 않고 폴백한다.** 깎으면 고장난 산출에서 그럴듯한 값이 나가고 결함이 가려진다. Governor의 D15와 같은 논리다.

## 4. 수식

`edge/pi/terrabyte_edge/irrigation/volume.py`. 증발산 모델은 엣지 RF 학습 도구에서 이식해, 엣지의 억제 판정과 관수량 산출이 같은 물리 가정을 쓰게 한다.

```
target_pct   = 작물별 목표 수분 (기본 35 %)
holding      = 0.45        # 배지 보수력
efficiency   = 0.85        # 배수·표면 유출 손실
wetted       = clip(sqrt(2000 / 용적), 0.35, 1.0)   # 1회 관수는 뿌리 영역만 적신다

redistribute = 1.4 * exp(-경과시간 / 3)
effective    = 토양수분 + redistribute
capacity_ml  = 용적 × holding × wetted
deficit_ml   = max(0, target_pct - effective)/100 × capacity_ml
lookahead_ml = ET(%/h) × 12h / 100 × capacity_ml × 0.5
volume_ml    = clip((deficit_ml + lookahead_ml) / efficiency, 0, 500)
```

`wetted`가 없으면 12L 화분에 340mL이 나와 Governor의 1회 200mL 상한에 항상 걸린다.

### 4.1. ⚠️ 이 값들은 문헌 기반 가정이다

`holding 0.45`, `efficiency 0.85`, `target 35%`, 그리고 작물별 목표 수분은 **실측이 아니다.** 특히 작물별 값은 `crop_score_profile`에 목표 토양수분이 없어(G3) 임의로 정한 것이다. 펌프 보정과 실제 배지가 확정되면 재보정이 필요하다.

### 4.2. 실측 데이터 전환 조건 (정정됨)

> **이전 문서의 조건이 틀렸다.** "관수 이벤트 200건 + `actual_ml` 기록"이라고 적었으나,
> `actual_ml`은 엣지가 `flow × runtime`으로 계산한 **우리 가정의 반향**이다. 그것으로 학습하면
> 모델은 식물이 아니라 유량 상수를 배운다.

실측 라벨에는 **물의 양을 실제로 잰 값**이 필요하다.

| 방법 | 비용 | 얻는 것 |
|---|---|---|
| 물통을 저울에 올리고 N회 관수 후 무게차 | 0 (부엌 저울) | 튜브·헤드 포함 **평균 전달량**, 드리프트 감지 |
| 화분 아래 로드셀 (HX711) | 약 5천원/화분 | **회당 실제 전달 질량** |
| 유량계 | 높음 | 회당 부피 직접 측정 |

최소 조건은 여전히 화분 5개 × 3주 × 관수 200건이되, **그중 전달량이 실측된 건이 포함돼야 한다.**

## 5. 펌프 보정 절차 (선행 작업)

`flow_ml_per_s`를 추정치에서 **오차 범위가 알려진 측정치**로 바꾼다. 20분이면 된다.

1. 실제 설치 상태(같은 튜브 길이·같은 높이차)에서 계량컵에 **10초씩 5회** 받는다
2. 평균과 표준편차를 낸다. 펌프마다 개체차가 크므로 **펌프 개수만큼 반복한다**
3. `app.irrigation.default-flow-ml-per-s`를 교체하고, 편차를 이 문서에 기록한다

측정된 편차가 이후 결정을 정한다.

- **±10% 이내** → mL 단위 유지할 만하다
- **±25% 이상** → 연속값 산출이 과잉이다. 폴백표 4단계가 오히려 정직한 해상도이며, 수식 출력을 그 단계로 양자화하는 편이 낫다

### G0 상세 — 클램프가 대부분의 용량을 결정한다

실기(Orange Pi)에서 측정한 실제 산출값이다. 기온 24℃·습도 55%·PPFD 300 기준.

| 화분 용적 | 토양수분 | 수식 산출 | Governor 통과 후 |
|---|---|---|---|
| 700 mL | 20 % | 87 mL | 87 mL |
| 700 mL | 32 % | 50 mL | 50 mL |
| **3 L** | 20 % | 305 mL | **200 mL (클램프)** |
| **3 L (와사비)** | 20 % | 370 mL | **200 mL (클램프)** |
| **6 L** | 20 % | 431 mL | **200 mL (클램프)** |
| **12 L** | 20 % | 500 mL (상한) | **200 mL (클램프)** |

**3L 이상에서는 305든 431이든 결과가 같다.** 수식의 정밀도가 결과에 영향을 주지 못한다.
`wetted_fraction`은 12L 화분의 과다 산출을 낮추려고 넣었으나 여전히 상한에 닿는다 — 그 완화는
목적을 달성하지 못했다.

이건 결함이라기보다 **정책과 수식이 서로 다른 전제 위에 있다**는 뜻이다.

- 수식의 전제: "목표 수분까지 채운다"
- Governor의 전제: "소량 다회 관수. 1회 200mL, 6시간 간격"

3L 화분을 20%에서 목표까지 채우려면 이 정책으로 최소 두 번, 6시간 이상 걸린다. 그게 의도된
동작인지, 아니면 큰 화분에 대해 간격이나 상한을 조정해야 하는지는 **펌프 보정(§5)과 실제 관찰
이후에 정할 문제**다. 지금 어느 쪽으로든 바꾸면 근거 없이 안전 한계를 건드리게 된다.

당장의 실무적 결론: **수식이 실질적 차이를 만드는 범위는 2L 미만 화분이다.**

## 7. 되돌아볼 조건

아래 중 하나라도 성립하면 이 문서의 D27·D28을 다시 검토한다.

- **전달량 실측 수단이 생겼다** — 라벨이 진짜가 되므로 학습 모델이 수식을 넘어설 수 있다
- **펌프 보정 편차가 ±10% 이내로 확인됐다** — 연속값 산출이 의미를 갖는 정밀도다
- **화분 종류·작물이 크게 늘었다** — 수식의 고정 함수형이 한계에 닿을 수 있다
